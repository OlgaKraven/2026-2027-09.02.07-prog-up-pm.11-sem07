ПМ.11 · Раздел М.1

Выбрать свой вариант и подготовить папку

  1. 1

    Одна собственная работа

    Прочитать общее задание целиком. Найти назначенную карточку в списке предметных областей и скачать только архив variant-NN.zip этой карточки. Номер NN в именах заменить своим номером. Магазин «Пара» ниже объясняет способ работы: отдельно создавать и сдавать демонстрацию не требуется.

  2. 2

    Распаковать и проверить файлы

    В Проводнике открыть скачанный ZIP → Извлечь всё → выбрать рабочую папку. Открыть data/variant-NN внутри распакованного комплекта. Проверить наличие products.csv, sizes.csv, stock.csv, users.csv, orders.csv и context.json. Не открывать CSV двойным щелчком для пересохранения в Excel: импортировать предоставленные файлы без изменения кодировки и заголовков.

    1. В кадре открыт пример выбора варианта 07. В работе открыть свой номер.
    2. CSV содержит строки данных; context.json содержит область, ожидаемые количества и историческую сумму.
  4. 3

    Создать рабочие папки

    В распакованном комплекте проверить папки sql, data, er, docs и checks. Недостающую папку создать: Проводник → Создать → Папку. Пять CSV и context.json своего варианта оставить в data/variant-NN. Сохранить исходные файлы без правок. В sql будут собственные SQL-файлы, в er — ER.pdf, в docs — описания полей и источников, в checks — журналы и результаты проверок.

    1. Пять папок имеют разное назначение. Пустые sql, er и checks заполняются по мере работы.
  6. 4

    Открыть контрольные значения

    В Блокноте выбрать Файл → Открыть, тип «Все файлы», затем data/variant-NN/context.json своего распакованного комплекта. Записать subject, rows и historical_order_total своего набора в раздел 1 отчёта. Для своих данных сверять собственные значения; числа магазина «Пара» относятся только к иллюстрациям.

    Проверка. В работе выбрана одна область и один исходный набор. Проверочные БД далее служат испытаниям этой же схемы.

ПМ.11 · Раздел М.2

Разобрать модель магазина «Пара»

  1. 1

    От модели к хранению

    Для магазина обуви «Пара» каждая модель имеет производителя, подкатегорию, цену, состав, описание и ссылку на изображение. Размер сам по себе не определяет остаток: доступное количество относится к паре «модель + размер». Поэтому product и stock_item — разные таблицы. В category и subcategory хранится иерархия; product ссылается только на subcategory, чтобы категория не дублировалась и не могла противоречить ей.

  2. 2

    Что означает третья нормальная форма

    Каждая строка описывает одну сущность, неключевые поля зависят от её ключа и не определяются другими неключевыми полями внутри той же таблицы. Производитель хранится в справочнике, а не повторяется текстом в каждом товаре. Заголовок sales_order описывает клиента и дату; order_line описывает конкретную позицию, количество и цену покупки. Вычисляемая сумма не хранится отдельно. unit_price является историческим фактом строки заказа и не должна обновляться вместе с product.price.

  3. 3

    Связать файлы и сущности

    products.csv описывает модель; stock.csv — остаток модели с конкретной маркировкой; users.csv — клиентов; orders.csv — заголовки и строки истории. Один заказ может занимать несколько исходных строк. Размерная позиция — сочетание модели и маркировки, например одной пары обуви и размера 36. В собственной области маркировкой может быть S, M, L либо другое значение своего CSV.

  4. 4

    Различить имена БД на снимках

    pm11_demo_visual — рабочая БД образца; pm11_check_visual — копия для намеренных ошибок; pm11_handoff_visual — проверка развёртывания из передаваемых файлов. В своём проекте использовать pm11_vNN, pm11_check_vNN и pm11_restore_vNN. Все три относятся к одной собственной схеме; демонстрационные данные в них не подставлять.

ПМ.11 · Раздел М.3

Запустить среду и создать собственную БД

  1. 1

    Запустить компоненты

    Открыть XAMPP Control Panel. Нажать Start в строках Apache и MySQL. Дождаться зелёной индикации и появления PID и порта. Нажать Admin в строке MySQL, чтобы открыть phpMyAdmin. Если компонент остановился, открыть Logs и сообщить преподавателю текст ошибки; не удалять файлы СУБД и не создавать таблицы при неработающем сервере.

    1. Зелёные строки и кнопки Stop означают, что компоненты сейчас работают.
    2. Кнопка Admin строки MySQL открывает phpMyAdmin.
  3. 2

    Создать БД

    В phpMyAdmin нажать «Создать БД» слева либо «Базы данных» сверху. Ввести свободное имя pm11_vNN. Выбрать сравнение utf8mb4_bin. Нажать «Создать». Не удалять занятую или чужую БД: выбрать другое собственное имя и записать замену в отчёт.

    1. Вместо имени образца ввести pm11_vNN своего варианта.
    2. Проверить utf8mb4_bin и нажать «Создать».
  5. 3

    Проверить выбранную БД

    Имя БД в верхней строке phpMyAdmin должно совпадать с собственным. В этой БД открыть вкладку SQL. Перед вставкой каждого нового запроса нажать «Очистить»: в редакторе может оставаться готовый SELECT предыдущей таблицы. Вставить законченный фрагмент и нажать «Вперёд». После ошибки прочитать её номер и текст до продолжения.

ПМ.11 · Раздел М.4

Сохранить собственный SQL-файл

  1. 1

    Создать файл в редакторе

    В Блокноте выбрать Файл → Создать. Ввести SQL своей схемы по разбору ниже. Каждый CREATE TABLE заканчивается точкой с запятой. Сначала сохранить файл, затем выполнять его законченный фрагмент в phpMyAdmin. Если блок помечен «продолжение», собрать все его части в одном файле до выполнения. Отдельный обрывок незаконченного CREATE TABLE не выполнять; команда заканчивается точкой с запятой. Не заменять файл историей запросов браузера.

    1. На вкладке видно расширение .sql; внизу окна — UTF-8.
    2. В образце первая часть создаёт справочники; затем идут модели, остатки и история.
  3. 2

    Сохранить в UTF-8

    Нажать Ctrl+Shift+S. Выбрать папку sql своего проекта. Указать имя 01_schema.sql, тип «Все файлы (*.*)», кодировку UTF-8 и нажать «Сохранить». Если оставить тип «Текстовые документы», может получиться 01_schema.sql.txt. Проверить окончание имени в Проводнике; при скрытых расширениях открыть Просмотреть → Показать → Расширения имён файлов.

    1. Имя должно заканчиваться на .sql, тип — «Все файлы», кодировка — UTF-8.

ПМ.11 · Раздел М.5

Определить сущности и ключи

  1. 1

    Первичные и внешние ключи

    Первичный ключ однозначно обозначает строку. AUTO_INCREMENT создаёт новые номера. Внешний ключ указывает на существующую строку другой таблицы. Для товара и размера нужен дополнительный UNIQUE: новый item_id не делает повторную пару модель-размер допустимой. RESTRICT защищает справочник или позицию, на которую ссылаются данные. CASCADE для строк заказа описывает их зависимость от заголовка; автоматическое возвращение остатков при удалении заказа этим не выполняется.

  2. 2

    Зафиксировать своё решение

    Составить список сущностей своей области и полей каждой сущности. Для каждого поля записать смысл, тип, допустимость пустого значения, первичный либо внешний ключ. Уникальная пара модель–маркировка запрещает два разных остатка одной позиции. Сверить названия и маркировки с собственными CSV. Отдельно указать, где хранится текущая цена и где — цена совершённой покупки.

ПМ.11 · Раздел М.6

Создать справочники

  1. 1

    Файл, место и смысл изменения

    Создать 01_schema.sql. Ввести этот фрагмент первым и выполнить во вкладке SQL выбранной БД. category обозначает крупную группу, subcategory — её вид; уникальность пары category_id/name разрешает одинаковое имя подкатегории в разных категориях. RESTRICT не даёт удалить категорию, пока на неё ссылается подкатегория. size хранит текстовый размер: в разных областях встречаются числовые размеры, S/M/L и универсальные маркировки. Проверить четыре таблицы на вкладке Структура; в каждой есть первичный ключ.

  2. 2.1

    Добавить строки 1–20 в 01_schema.sql

    -- === Справочники и третья нормальная форма
CREATE TABLE category (
 category_id BIGINT PRIMARY KEY AUTO_INCREMENT,
 name VARCHAR(120) NOT NULL UNIQUE CHECK (TRIM(name)<>'')
) ENGINE=InnoDB;
CREATE TABLE subcategory (
 subcategory_id BIGINT PRIMARY KEY AUTO_INCREMENT,
 category_id BIGINT NOT NULL,
 name VARCHAR(120) NOT NULL,
 UNIQUE(category_id,name),
 FOREIGN KEY(category_id) REFERENCES category(category_id) ON DELETE RESTRICT
) ENGINE=InnoDB;
  3. 2.2

    Добавить строки 1–20 в 01_schema.sql · продолжение

    CREATE TABLE manufacturer (
 manufacturer_id BIGINT PRIMARY KEY AUTO_INCREMENT,
 name VARCHAR(120) NOT NULL UNIQUE
) ENGINE=InnoDB;
CREATE TABLE size (
 size_id BIGINT PRIMARY KEY AUTO_INCREMENT,
 label VARCHAR(30) NOT NULL UNIQUE
) ENGINE=InnoDB;
    1. Проверить имя выбранной БД. Перед новым текстом нажать «Очистить».
    2. Выполнить только текущий законченный фрагмент кнопкой «Вперёд»; уже созданные таблицы повторно не создавать.
    1. Для CREATE TABLE сообщение о пустом результате нормально: эта команда создаёт таблицу и не возвращает строки.
    2. Фактическое наличие таблиц проверить на вкладке «Структура».

ПМ.11 · Раздел М.7

Создать модели и размерные позиции

  1. 1

    Файл, место и смысл изменения

    Добавить фрагмент в конец 01_schema.sql и выполнить только новые CREATE TABLE. product хранит свойства модели, а stock_item — остаток по размеру. DECIMAL хранит денежные значения точно; FLOAT для цены не используется. Ограничение available>=0 действует независимо от клиента, UNIQUE(product_id,size_id) не позволяет повторную позицию. image_path — имя исходного изображения: файлы находятся в Images рядом с демонстрационными CSV; поле является ссылкой на файл, а не бинарным содержимым картинки. В структуре stock_item откройте Связи и проверьте оба внешних ключа.

  2. 2.1

    Добавить строки 21–43 в 01_schema.sql

    -- === Товар и сочетание модели с размером
CREATE TABLE product (
 product_id BIGINT PRIMARY KEY AUTO_INCREMENT,
 subcategory_id BIGINT NOT NULL,
 manufacturer_id BIGINT NOT NULL,
 name VARCHAR(200) NOT NULL,
 image_path VARCHAR(255) NOT NULL DEFAULT '',
 description TEXT NOT NULL,
 composition TEXT NOT NULL,
 price DECIMAL(12,2) NOT NULL CHECK(price>0),
 UNIQUE(name,manufacturer_id),
 FOREIGN KEY(subcategory_id) REFERENCES subcategory(subcategory_id) ON DELETE RESTRICT,
 FOREIGN KEY(manufacturer_id) REFERENCES manufacturer(manufacturer_id) ON DELETE RESTRICT
) ENGINE=InnoDB;
  3. 2.2

    Добавить строки 21–43 в 01_schema.sql · продолжение

    CREATE TABLE stock_item (
 item_id BIGINT PRIMARY KEY AUTO_INCREMENT,
 product_id BIGINT NOT NULL,
 size_id BIGINT NOT NULL,
 available INT NOT NULL CHECK(available>=0),
 UNIQUE(product_id,size_id),
 FOREIGN KEY(product_id) REFERENCES product(product_id) ON DELETE RESTRICT,
 FOREIGN KEY(size_id) REFERENCES size(size_id) ON DELETE RESTRICT
) ENGINE=InnoDB;

ПМ.11 · Раздел М.8

Создать клиентов и историю заказов

  1. 1

    Файл, место и смысл изменения

    Добавить заключительный фрагмент в тот же файл и выполнить. app_role описывает роли клиентов исходной предметной области; эти записи не дают прав подключения к серверу. sales_order содержит клиента и дату. order_line имеет составной первичный ключ: одна позиция присутствует в заказе один раз с суммарным количеством. unit_price фиксирует цену покупки. Открыть Структура и проверьте десять предметных таблиц. Далее перейти к следующим этапам «Проверить структуру, уникальность и ссылки» и «Получить ER-диаграмму и экспортировать PDF».

  2. 2.1

    Добавить строки 44–72 в 01_schema.sql

    -- === Клиент, заголовок заказа и исторические строки
CREATE TABLE app_role (
 role_id BIGINT PRIMARY KEY AUTO_INCREMENT,
 name VARCHAR(80) NOT NULL UNIQUE
) ENGINE=InnoDB;
CREATE TABLE customer (
 customer_id BIGINT PRIMARY KEY AUTO_INCREMENT,
 login VARCHAR(80) NOT NULL UNIQUE,
 last_name VARCHAR(80) NOT NULL,
 first_name VARCHAR(80) NOT NULL,
 patronymic VARCHAR(80) NOT NULL DEFAULT '',
 role_id BIGINT NOT NULL,
 FOREIGN KEY(role_id) REFERENCES app_role(role_id) ON DELETE RESTRICT
) ENGINE=InnoDB;
  3. 2.2

    Добавить строки 44–72 в 01_schema.sql · продолжение

    CREATE TABLE sales_order (
 order_id BIGINT PRIMARY KEY AUTO_INCREMENT,
 customer_id BIGINT NOT NULL,
 ordered_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
 FOREIGN KEY(customer_id) REFERENCES customer(customer_id) ON DELETE RESTRICT
) ENGINE=InnoDB;
  4. 2.3

    Добавить строки 44–72 в 01_schema.sql · продолжение

    CREATE TABLE order_line (
 order_id BIGINT NOT NULL,
 item_id BIGINT NOT NULL,
 quantity INT NOT NULL CHECK(quantity>0),
 unit_price DECIMAL(12,2) NOT NULL CHECK(unit_price>0),
 PRIMARY KEY(order_id,item_id),
 FOREIGN KEY(order_id) REFERENCES sales_order(order_id) ON DELETE CASCADE,
 FOREIGN KEY(item_id) REFERENCES stock_item(item_id) ON DELETE RESTRICT
) ENGINE=InnoDB;

ПМ.11 · Раздел М.9

Проверить структуру, уникальность и ссылки

    1. В образце десять предметных таблиц. stg_таблицы будут добавлены позже.
    2. Перед созданием промежуточного слоя проверить движок InnoDB и наличие всех своих таблиц.
  2. 1

    Проверить размерную позицию

    В строке stock_item нажать «Структура». В разделе «Индексы» найти PRIMARY по item_id и уникальный индекс из двух полей product_id и size_id. Значение «Да» относится к паре целиком: это не два независимых уникальных поля.

    1. PRIMARY обозначает идентификатор строки.
    2. Две строки product_id и size_id относятся к одному уникальному индексу product_id.
  4. 2

    Открыть внешние ключи

    В структуре stock_item открыть «Связи». Проверить product_id → product.product_id и size_id → size.size_id. Проверить ON DELETE RESTRICT. Здесь выполняется проверка созданных SQL-ограничений; дополнительные пустые строки формы заполнять не требуется.

    1. Первая ссылка ведёт на модель, вторая — на справочник маркировок.
    1. RESTRICT препятствует удалению строки справочника, на которую ссылается позиция.
  7. 3

    Проверить остальные связи

    Аналогично открыть product и order_line. В product проверить связи с manufacturer и subcategory; в order_line — с sales_order и stock_item. Для строк заказа правило CASCADE у ссылки на заголовок задано осознанно. Записать объяснение в словарь полей.

    Проверка. ER и SQL описывают одни и те же ключи и связи.

ПМ.11 · Раздел М.10

Получить ER-диаграмму и экспортировать PDF

  1. 1

    Открыть Дизайнер

    Открыть собственную БД, вкладку «Структура» → «Ещё» → «Дизайнер». Делать это после десяти предметных таблиц и до создания stg_таблиц и представлений. При другом количестве собственных сущностей ориентироваться на свою принятую модель.

    1. Меню «Ещё» находится справа от вкладок БД. Выбрать «Дизайнер».
  3. 2

    Разместить таблицы

    Перетащить каждую таблицу за строку её названия. Разнести таблицы, чтобы заголовки и поля не перекрывались. Увеличить рабочее окно при необходимости. Связи берутся из внешних ключей InnoDB: рисование похожей линии не заменяет SQL-ограничение.

    1. Справочники находятся слева, модели и остатки — в центре, история заказов — справа. Подробные фрагменты показаны ниже.
    1. subcategory хранит category_id; категория не дублируется текстом в каждой модели.
    1. product хранит свойства модели и текущую цену.
    2. stock_item ссылается на product и size и хранит available — остаток конкретной позиции.
    1. sales_order хранит клиента и дату.
    2. order_line хранит quantity и unit_price. Цена покупки не берётся из текущего прайса.
  8. 3

    Выбрать параметры экспорта

    1. Зелёная строка сообщает о чтении файла, красный блок — об отказе CALL import_checked().
    2. Перейти к журналу import_issue; не отключать проверки.
  4. 3

    Найти координаты и причины

    SELECT source_file,source_row,issue_code,reason
FROM import_issue WHERE disposition='отклонено'
ORDER BY source_file,source_row;
    1. stock_link указывает на неизвестную модель; quantity_price — на нулевое количество.
    2. В образце есть и order_item: заказ ссылается на испорченную позицию. Две внесённые ошибки могут породить несколько связанных записей журнала.
  6. 4

    Проверить пустые предметные таблицы

    SELECT (SELECT COUNT(*) FROM product) AS models,
 (SELECT COUNT(*) FROM stock_item) AS positions,
 (SELECT COUNT(*) FROM customer) AS customers,
 (SELECT COUNT(*) FROM sales_order) AS orders,
 (SELECT COUNT(*) FROM order_line) AS order_lines;
    1. Все пять счётчиков равны 0. Предметные строки не были перенесены частично.

ПМ.11 · Раздел М.22

Проверить историческую цену и откат

  1. 1

    Выполнить весь опыт одним SQL-блоком

    На принятой проверочной копии открыть SQL, очистить поле и выполнить весь следующий блок целиком. @pid — номер модели одной строки исходного заказа. Значения с @ живут в одном подключении; не разбивать опыт на разные нажатия «Вперёд». До опыта записать текущую цену и итог истории.

  2. 2

    Цена до изменения, после изменения и после ROLLBACK

    START TRANSACTION;
SET @pid := (SELECT s.product_id FROM stock_item s
 JOIN order_line l USING(item_id) ORDER BY l.order_id,l.item_id LIMIT 1);
SELECT 'before' AS phase,price AS current_price,
 (SELECT SUM(quantity*unit_price) FROM order_line) AS history_total
FROM product WHERE product_id=@pid;
UPDATE product SET price=price+17 WHERE product_id=@pid;
SELECT 'after' AS phase,price AS current_price,
 (SELECT SUM(quantity*unit_price) FROM order_line) AS history_total
FROM product WHERE product_id=@pid;
ROLLBACK;
SELECT 'restored' AS phase,price AS current_price,
 (SELECT SUM(quantity*unit_price) FROM order_line) AS history_total
FROM product WHERE product_id=@pid;
    1. before — исходное состояние. У образца текущая цена 2190.00, сумма истории 341770.00.
    1. after — текущая цена увеличена на 17; историческая сумма не изменилась.
    2. Для своего варианта исходная цена и сумма берутся из собственной БД.
    1. restored — цена восстановлена. ROLLBACK завершает проверочный опыт без сохранения изменения.
  6. 3

    Объяснить результат

    История считается по order_line.unit_price, зафиксированной при покупке. Изменение product.price меняет текущий прайс и не пересчитывает старые заказы. В отчёте сохранить отдельные состояния до и после и указать наблюдавшиеся числа.

    Проверка. После отката счётчики, остатки и историческая сумма совпадают с принятым состоянием.

ПМ.11 · Раздел М.23

Проверить три ограничения

  1. 1

    Выполнять опыты отдельно

    Использовать только принятую проверочную БД. Сначала сохранить контрольные счётчики и суммы. Каждый запрос ниже выполнить отдельным нажатием «Вперёд»: ожидаемая ошибка прерывает текущий пакет команд. После каждого отказа снова открыть SQL и очистить редактор.

  2. 2

    Повторная пара модели и маркировки

    INSERT INTO stock_item(product_id,size_id,available)
SELECT product_id,size_id,available FROM stock_item ORDER BY item_id LIMIT 1;
    1. #1062 означает, что пара product_id,size_id уже существует. Новая предметная строка не принимается.
  4. 3

    Отрицательный остаток

    UPDATE stock_item SET available=-1 ORDER BY item_id LIMIT 1;
    1. #4025 сообщает о нарушении available>=0. Отрицательный остаток не сохранён.
  6. 4

    Ссылка на отсутствующую модель

    INSERT INTO stock_item(product_id,size_id,available)
SELECT MAX(product_id)+1000,(SELECT MIN(size_id) FROM size),0 FROM product;
    1. #1452 сообщает о нарушении внешнего ключа. Не отключать FOREIGN_KEY_CHECKS.
  8. 5

    Допустимое изменение с возвратом состояния

    START TRANSACTION;
SELECT item_id,available FROM stock_item ORDER BY item_id LIMIT 1;
UPDATE stock_item SET available=available+1 ORDER BY item_id LIMIT 1;
SELECT item_id,available FROM stock_item ORDER BY item_id LIMIT 1;
ROLLBACK;
  9. 6

    Сверить сохранение состояния

    Повторить контроль счётчиков и сумм после трёх отказов и допустимого изменения с ROLLBACK. Успех отрицательного опыта — конкретный отказ и сохранённые данные. Само наличие красного сообщения без проверки состояния недостаточно.

    1. Счётчики, остатки и сумма истории совпали с принятым состоянием.
